# Пересечения выходов и слотов

В календаре `В` соответствует `visits.slot IN ('DAY', 'MORNING')`, а `И` —
`EVENING/FULL_INVENT`. Ранее реестр выбирал только одинаковые MORNING/EVENING:
`_valid_intersection_candidates` исключал DAY. Форма предлагает MORNING/EVENING
в пятницу/субботу, DAY — в остальные дни; поэтому обычные дни пропускались.

Для пары разных `merchant_id` на `point_code + visit_date` общие MORNING/EVENING
имеют приоритет: выводятся только эти слотные строки, без CALENDAR_DAY.
Если общего конкретного слота нет, оба имеют DAY/MORNING/EVENING на этой ТТ
и дате и хотя бы один имеет DAY, выводится ровно один CALENDAR_DAY.
DAY/MORNING, DAY/EVENING и DAY/DAY дают fallback; MORNING/EVENING у разных
сотрудников не пересекаются. Одного совпадения даты недостаточно. Legacy FULL_INVENT
не добавляет календарный fallback. DISTINCT исключает технические повторы.
Слотные исключения «Не принимал поставку» сохранены и не обходятся fallback.

`get_intersections_rows(..., include_calendar_days=True)` включает слоты и fallback.
Прежний вызов без флага и `find_visit_intersections` сохраняют слотный контракт.
Административный реестр использует оба уровня для `has_overlap`.

Excel `peresecheniya` сохраняет первые восемь столбцов и прежние слотные строки.
Добавлены уровень и ID сотрудников. `CALENDAR_DAY` — обозначение уровня отчёта,
не новое значение в БД. Лист «По дням» содержит одну строку на ТТ + дату, «Итоги»
различает число ТТ-дней, календарных дат, дней с fallback и пар по слотам.
Нельзя считать число строк первого листа числом дней: день может иметь несколько
пар сотрудников и MORNING/EVENING. Фильтр ТУ включает пару, если в ТУ есть хотя бы
один из участников, как и ранее.

DB schema unchanged. Пересечения вычисляются при чтении, backfill не нужен.
Сохранение выходов, формы, статусы, поставки и расчёт выплат не меняются.
Источник дат — `visits`; monthly/point submissions не являются версиями дневных
отметок и не фильтруют их. Draft и submitted учитываются одинаково. Агрегат числа
выходов сам по себе не создаёт дат. Если указанного числа нет в текущем расчёте,
нужно сверять фактические строки, а не восстанавливать предполагаемый календарь.

## Диагностика сентября

Из корня версии с исправлением, в уже настроенном окружении с доступом к БД:

```sh
python -m app.intersection_audit --year 2026 --month 9 --dry-run --output /secure/local/september-intersections.json
```

Путь — пример; выберите новый защищённый локальный файл вне Git. Не передавайте
DATABASE_URL в командной строке. Используются существующие DATABASE_URL и
SECRET_SALT окружения; не публикуйте окружение или отчёт с ФИО.

Команда открывает PostgreSQL REPEATABLE READ / READ ONLY транзакцию, выполняет
только чтение и завершает её rollback. Нет миграций, инициализации приложения,
режима записи или параметра apply. Существующий файл отчёта не перезаписывается.

JSON содержит число ТТ, ТТ-дней и отдельных дат до/после, число слотных пар,
новые ТТ-дни и ранее пропущенные пары, сохранённые слотные пересечения,
повторные записи посещений, самопересечения и отдельный раздел 3284.
«До» — прежний алгоритм на том же снимке данных, а не сохранённая старая выгрузка.

Контрольный автоматический fixture: Сотрудник Первый и Сотрудник Второй, ТТ 3284, сентябрь 2026. Дни В: 01, 02, 03, 04, 07, 08, 09, 10, 11.
Для 04/11 fixture включает у обоих MORNING и EVENING: 4 слотные пары сохраняются,
а уникальных ТТ-дней становится 9 вместо 2. Это синтетический regression fixture
по условию задачи, не подтверждение фактических записей production.

Статистика всего production-сентября требует запуска read-only команды с
действующим доступом. Результат fixture нельзя выдавать за такую статистику.
