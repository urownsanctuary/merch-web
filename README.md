# Merch Web

Внутренний сервис сверки работы мерчендайзеров микромаркетов.

## Назначение

- Отметка выходов и учёт поставок.
- Полный инвент и учёт дней работы с кофемашиной.
- Примечания, возмещения и прикрепление чеков.
- Месячная сверка и фиксация отправленных результатов.
- Административные отчёты и Excel-выгрузки.

## Архитектура

Приложение на FastAPI использует SQLAlchemy и PostgreSQL. HTML-страницы
формируются приложением; файлы чеков хранятся в PostgreSQL.
Production размещён на FirstVDS: Docker Compose управляет приложением,
PostgreSQL и nginx, внешний адрес — [https://sverka-mm.ru](https://sverka-mm.ru).
Доступ пользователей осуществляется по HTTPS.

Поставляемый Compose содержит HTTP-конфигурацию nginx; параметры действующего
TLS-контура и сертификаты передаются командой эксплуатации отдельно.
Порядок проверки конфигурации описан в [VPS runbook](docs/VPS_RUNBOOK.md).

## Локальный запуск

Требуются Python 3.12 и отдельная PostgreSQL с подготовленной схемой и тестовыми
данными. Полного bootstrap базовых таблиц в репозитории нет: пустая БД не является
готовым окружением. Получите у команды поддерживаемый обезличенный набор данных
и порядок его восстановления. Production БД для локального запуска не используется.

Из корня проекта создайте окружение:

```sh
python -m venv .venv
```

Активируйте его: `source .venv/bin/activate` в POSIX shell или
`.\.venv\Scripts\Activate.ps1` в PowerShell. Затем:

```sh
python -m pip install -r requirements.txt
```

Задайте обязательные переменные из следующего раздела в окружении процесса,
используя отдельные локальные секреты. Для локального HTTP установите
`ENVIRONMENT=development`, `AUTO_SYNC_PRODUCTION_CALENDAR=0` и `MAINTENANCE_MODE=0`.
Приложение само не загружает `.env`.

```sh
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Откройте `http://127.0.0.1:8000/login-page`; проверка соединения с БД — `/db-check`.
Обычный startup не выполняет миграции, backfill или синхронизацию календаря.
Для уже подготовленной отдельной БД прежние дополнения схемы запускаются только
явной командой `python -m app.schema_setup --apply` после проверки цели.
Это записывающая maintenance-операция, не часть запуска HTTP-сервера и не полный
bootstrap пустой БД. Правила production — в runbook.

## Environment variables

Значения секретов хранятся вне Git. Имена и назначение переменных:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | Обязательная строка подключения к PostgreSQL |
| `ADMIN_LOGIN`, `ADMIN_PASSWORD` | Обязательные учётные данные администратора |
| `SECRET_SALT` | Обязательный секрет для существующих хешей и административной сессии |
| `SESSION_SECRET` | Отдельный секрет подписи сессий, не короче 24 символов; обязателен в Compose. Код допускает fallback на `SECRET_SALT` |
| `ENVIRONMENT` | Режим secure-cookie: `production` для HTTPS, `development` для локального HTTP, `test` для тестов |
| `AUTO_SYNC_PRODUCTION_CALENDAR` | Legacy-настройка: больше не запускает запись при startup, даже если равна `1`. Синхронизация выполняется явно через административное действие или CLI календаря |
| `MAINTENANCE_MODE` | Режим обслуживания с блокировкой запросов изменения данных |
| `MAX_RECEIPT_BYTES` | Лимит одного чека в байтах; default кода — 15 MiB, пример env задаёт 5 MiB |

Compose также использует обязательные `POSTGRES_DB`, `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `APP_GIT_SHA` и необязательные `SERVER_NAME`, `HTTP_BIND_IP`,
`HTTP_PORT`. В Compose `ENVIRONMENT` фиксирован как `production`.
Образ задаёт `PYTHONPATH`, `PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED`.

Скрипты эксплуатации используют `SALARY_ENV_FILE`, `PROJECT_DIR`, `BACKUP_DIR`,
`BACKUP_RETENTION_DAYS`, `BASE_URL`; Docker Compose учитывает `COMPOSE_FILE`, если
он задан для конфигурации площадки. Переменные shell `TARGET_SHA`, `PREVIOUS_SHA`
и `ROLLBACK_SHA` используются в runbook для выбора релиза.

Формат конфигурации: [production.env.example](deploy/env/production.env.example).
Передача поддержки не требует смены действующих секретов: их замена проводится
отдельно с учётом влияния на хеши и сессии.

## Совместные выходы и принятие поставки

Факт присутствия по-прежнему хранится в `visits`. Таблица
`visit_payment_roles` задаёт роль оплаты обычного выхода для
`merchant_id + point_code + visit_date`: `NO_SUPPLY` либо `RECEIVER`.
На ещё не затронутых новой функцией днях сохраняется прежний расчёт по коробкам
и `pay_lt5`. При включённой функции первый обычный выход тоже получает явный
`RECEIVER`. На управляемом дне личный расчёт и admin/payroll используют один
общий SQL-предикат: supply оплачивается только активному `RECEIVER`.
Отсутствие роли у другого сотрудника не создаёт второго получателя.
Неоднозначные legacy-дни с несколькими автоматическими получателями не
переписываются: новое распределение блокируется для разбора администратором.
Оплачиваемая поставка определяется общей функцией `effective_has_supply`;
роль не создаёт поставку, если действующие данные поставок её не подтверждают.
`DAY/MORNING` используют роль и текущую ставку ТТ. `EVENING/FULL_INVENT`,
недельное ограничение инвента, маркеры `В`/`И` и правила coffee не меняются.

Перед вторым выходом пользователь подтверждает присутствие. При оплачиваемой
поставке обычный выход предлагает два варианта: без принятия поставки
(первый сотрудник остаётся без изменений) либо принятие поставки
(первый получает роль `NO_SUPPLY`, второй — `RECEIVER`). Примечания и денежные
корректировки при этом не создаются. Инвентаризационный выход требует только
подтверждения совместного присутствия и сохраняет прежнюю инвентаризационную оплату.

`delivery_events` хранит идентификатор запроса, вид события, участников,
идентификаторы выходов и инициатора. Для `TRANSFER` сохраняются снимки ФИО,
полных телефонов, типов и ставок на момент изменения. Ссылки на выходы мягкие:
история сохраняется, даже если пользователь впоследствии уберёт свою отметку.
Текущая роль привязана к активному visit; удаление обычного выхода удаляет его
роль в той же транзакции. Если удаляется receiver, ранее уступивший поставку
сотрудник с ещё активным выходом получает роль обратно, если его месяц открыт
и восстановление безопасно. Создаётся `RECEIVER_RESTORED` со снимком ставок.
Если кандидат отсутствует, закрыт или неоднозначен, удаление при других активных
выходах блокируется с `EXCEPTION_DELETE_RECEIVER`; деньги остаются прежними.
При отсутствии других обычных выходов receiver удаляется без назначения нового.
Удаление NO_SUPPLY не меняет действующего receiver. После удаления всех выходов
активных ролей нет. Повторная отметка проходит новый flow; audit никогда не
используется для восстановления текущей роли. Смена роли сама по себе не
добавляет выход или день coffee. Поле `source` отделяет источник решения
от факта присутствия и допускает последующую интеграцию с LogOps.

PostgreSQL сериализует операции блокировкой ТТ/даты и блокировками строк
сотрудников в порядке ID. Monthly submit использует ту же блокировку сотрудника.
Частичный UNIQUE запрещает двух текущих receiver на ТТ/дату. PostgreSQL FK
связывает роль с точными visit_id/merchant_id/ТТ/датой и удаляет её каскадно
при удалении visit. Текущий receiver хранит возможность первой передачи и ID
кандидата и его точный visit_id для обратного восстановления. Удаление этого
выхода отменяет кандидатуру, даже если тот же сотрудник позже отметится снова;
история событий для этого не читается.
Повторный `TRANSFER` после нового жизненного цикла допустим; UNIQUE request_key
предотвращает повтор события одного запроса. Подписанные формы фиксируют дату, действие,
контекст подтверждения и ключ идемпотентности; повтор POST не переключает
сохранённый выход обратно. Все изменения и событие фиксируются одной транзакцией.

Уже подтверждённое принятие поставки, закрытая сверка первого сотрудника,
неоднозначные старые выходы или прежняя корректировка создают исключение
для администратора без автоматического изменения выплат. Старую корректировку
«не принимал поставку» нельзя применить после совместного решения по роли.
До такого решения у одиночного выхода прежняя корректировка доступна; её
наличие затем блокирует передачу поставки, предотвращая двойное вычитание. Исторические
корректировки автоматически не переписываются.

В административном отчёте доступны:

- «Изменённые выходы мерчендайзеров по ставкам» —
  `/admin-export-delivery-changes?year=YYYY&month=M`, XLSX только событий
  перераспределения и обратного восстановления: дата, ТТ, участники, полные телефоны, ставки до/после,
  время и ID события. Колонки «Причина изменения» нет. Данные берутся из снимков.
- «Выходы, требующие разбора» — `/admin-delivery-exceptions?year=YYYY&month=M`.
  Решения по исключениям принимает администратор; автоматического исправления нет.
- В существующей выгрузке пересечений добавлен признак подтверждённого совместного
  выхода. Существующие строки, уровни пересечений и листы сохранены.

Эти две новые административные страницы показывают выбранный месяц целиком;
фильтр ТУ основного отчёта к ним не применяется.

### Телефоны и совместимость входа

`merchants.phone` хранит 11 цифр, начальная `8` нормализуется в `7`.
Новый формат импорта: `ФИО`, `Телефон`, `ТУ`; ТУ можно задать общей формой.
`last4` вычисляется из телефона. Если файл содержит обе колонки, несовпадение
отклоняет весь файл с номером строки. Старый импорт `ФИО` + `Последние 4`
работает; у новых старых записей телефон остаётся пустым, у существующей
совпавшей записи известный телефон сохраняется. Сопоставление импорта по
нормализованному ФИО и last4 сохраняет прежний `merchant_id`; смену реквизитов
существующего сотрудника следует делать в его admin-карточке по ID.

Полный телефон доступен только административному интерфейсу и защищённой
выгрузке. Он не помещается в сессии, URL, пользовательские страницы или логи.
Вход остаётся «ФИО + последние 4 цифры»; новые подписанные сессии дополнительно
содержат стабильный `merchant_id`. Старые FIO-only cookie отклоняются и очищаются:
потребуется один раз войти заново. Несуществующий или неактивный merchant_id
также приводит к очистке cookie и входу заново. ФИО не заменяет ID при определении
владельца данных, включая чеки. Административная авторизация независима.

### Явная миграция и проверка

Перед запуском новой версии требуется добавочная миграция. HTTP startup
её не выполняет. Команды используют уже настроенный целевой `DATABASE_URL`:

```sh
python -m app.delivery_migration --dry-run
python -m app.delivery_migration --apply
python -m app.delivery_migration --dry-run
```

Без аргументов выполняется dry-run. Миграция добавляет `phone`, две таблицы
и индексы/FK; не меняет прежние выходы, суммы, ставки или примечания. Повторное
применение не создаёт дубли. Backfill не требуется. Для production применение
миграции и выпуск требуют отдельного разрешения. После появления новых ролей
нельзя откатывать только код на старый калькулятор, игнорирующий эти роли.

Dry-run и apply сначала выполняют одинаковый preflight до любого DDL, в том
числе при повторном запуске. Проверяются обязательные колонки, типы, nullable,
defaults, PK, UNIQUE, CHECK, определения именованных индексов и FK. Дубли
receiver, идентичностей ролей/выходов, request keys, осиротевшие роли и неверные
кандидаты восстановления приводят к STOP: diagnostic содержит только код
проблемы и количество конфликтов. Данные автоматически не исправляются.
Отсутствующие таблицы, phone, штатные индексы и FK безопасно доустанавливаются;
повреждённая существующая таблица требует отдельного разбора без изменения БД.
Отчёт успешного preflight содержит план SQL без персональных данных.

PostgreSQL удерживает блокировки проверяемых таблиц до завершения транзакции,
чтобы записи не изменились между проверкой и DDL; ожидание блокировки ограничено
пятью секундами. Запускайте миграцию в согласованном окне. При обновлении от
предыдущей, ещё не выпущенной версии PR снимается только индекс
`uq_delivery_transfer` с проверенным прежним определением. Legacy-индексы
production не удаляются. Неполные таблицы старого формата не достраиваются
автоматически, даже если они пусты.

Административный preview `/admin-data` распознаёт `visit_payment_roles` и
`delivery_events` как сохраняемые данные. Их строки и телефоны не выводятся
в preview; сброс реквизитов сохраняет текущее состояние оплаты и audit.
Неизвестные таблицы с merchant_id по-прежнему блокируют preview для разбора.

### Безопасный выпуск с feature flag

`DELIVERY_ROLE_FLOW_ENABLED` по умолчанию **0**, в том числе когда переменной
вообще нет. Compose передаёт её приложению. При OFF на нетронутых днях работает
прежний flow, новые роли и delivery events не создаются. Уже созданные роли
всегда участвуют в расчёте; при OFF изменение таких дней блокируется. Поэтому
выключение флага после использования функции не является финансовым rollback.

Порядок после отдельного разрешения на rollout:

1. Создать и проверить резервную копию БД штатным способом.
2. Выполнить `app.delivery_migration --dry-run`, затем `--apply`, затем повторный
   dry-run. Ожидать ноль операций после apply; при ошибке остановиться.
3. Развернуть новый SHA со значением флага 0. Проверить SHA, health, login,
   admin, старые расчёты и выгрузки. FIO-only пользователи войдут заново.
4. Убедиться, что `visit_payment_roles` и `delivery_events` пусты. До активации
   приложение можно откатить на прежний SHA без rollback схемы.
5. После успешных проверок и отдельного разрешения включить флаг явно,
   пересоздав app штатным процессом с тем же SHA. Не смешивать старые и новые
   workers с разными настройками. Изменять env-файл недостаточно: существующий
   контейнер не перечитывает environment сам.
6. После появления ролей/events старый application-only rollback запрещён.
   При проблеме выключить новые действия (OFF сохраняет расчёт и замораживает
   управляемые дни) либо включить maintenance; исправление выполнять вперёд.
   Ничего не удалять из state/audit и не восстанавливать БД автоматически.

Обычный pytest проверяет SQLite, HTTP, импорт, экспорт и совместимость. Для
реальных конкурентных проверок задайте `TEST_DELIVERY_POSTGRES_URL` на отдельный
одноразовый PostgreSQL **на localhost** и запустите
`python -m pytest tests/test_delivery_postgres.py -q`.
Тесты создают отдельные случайные схемы и оставляют их для диагностики;
production-подключения использовать нельзя.
